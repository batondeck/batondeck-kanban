## Ticket states (fixed; owner rulings 2026-10-22)

**Six statuses.** Conductor's eight (`src/domain/status.ts:19-28`) minus `CANCELLED` and `DEAD_LETTER`:

| Status | Column default | Entered by (conductor, verified) | Left by |
|---|---|---|---|
| `BACKLOG` | Backlog | `create_task` lands in the **first column's status** (`tasks.ts:102,151`), BACKLOG on the default board | move_task |
| `READY` | Ready | move_task, release_task, handoff_task (`lifecycle.ts:1166`), fail_task retryable (`:244`), reap_stale_leases, auto-unblock, run resolution | claim_task / claim_next / move_task |
| `IN_PROGRESS` | In progress | claim (lease), move_task | complete / block / release / handoff / fail / reap |
| `BLOCKED` | Blocked | block_task, add_subtask / orchestrate_subtasks (store `:3819`), move_task promote-with-deps (`tasks.ts:421`), **fail_task when poisoned**. (`add_dependency` only writes `blockedBy`, store `:3611-3680` — it does not change status.) | auto-unblock (→ READY), move_task |
| `REVIEW` | Review | complete_task when the **project** setting `reviewEnabled` is on (`lifecycle.ts:782`, `types.ts:501`) | move_task → DONE or back to IN_PROGRESS |
| `DONE` | Done | complete_task (`reviewEnabled` off) or move_task from REVIEW | move_task → IN_PROGRESS (reopen) |

The transition table is **closed** (every state is in it) and **not editable**:

```
BACKLOG     → READY
READY       → IN_PROGRESS, BACKLOG
IN_PROGRESS → REVIEW, BLOCKED, READY
BLOCKED     → IN_PROGRESS, READY
REVIEW      → DONE, IN_PROGRESS
DONE        → IN_PROGRESS
```

This is conductor's `DEFAULT_TRANSITION_TABLE` (`status.ts:35-43`) with the `CANCELLED` targets removed.
A move to the same status is always legal (reorder within a column, `status.ts:50`). An illegal move
returns `INVALID_TRANSITION` with the allowed next statuses and the shortest legal path (`status.ts:64`).
Auto-unblock and WIP limits (IN_PROGRESS column only) stay as server-enforced automatics.

### Fold 1 — `DEAD_LETTER` → `BLOCKED` (poison)

Why: a hidden state outside the table, entered by `fail_task`/reaper after `poisonAfterAttempts`
(per-project `retryPolicy`, `types.ts:629`; `retry.ts:36`) **or on `retryable:false` regardless of
attempts** (`lifecycle.ts:222-248`), left only by `requeue_task` (`:1085-1121`).

- A poisoned task moves to `BLOCKED` with `blockedReason: "poison"`; `claimAttempts` is kept. One event
  type `task.poisoned` (the rename of `task.dead_lettered`, done once).
- **Both auto-unblock guards key on `blockedReason`**: `unblock.ts:35` and store `:3673` currently
  treat `BLOCKED` + empty `blockedBy` as "→ READY", which would un-poison a task whose last dependency
  finishes. Fix: `autoReady = blockedBy.length === 0 && status === 'BLOCKED' && blockedReason !== 'poison'`.
- `isClaimable` keys on `blockedReason === 'poison'`, not on an attempt count.
- Requeue is `move_task BLOCKED → READY`, which resets `claimAttempts` to 0 — and **from
  `blockedReason:'poison'` it requires the master role**, because conductor's `requeue_task` is
  master-gated (`lifecycle.ts:1088`) so a worker cannot un-poison its own ticket. `requeue_task` is not
  ported.
- `reap_stale_leases` and the lazy recovery in `next_task`/`claim_next` write READY-with-backoff or
  BLOCKED-poison, never a third state.
- Consumers: the `deadLetter` buckets in `lifecycle.ts:1257` and `sprints.ts:326/340` become
  `poisoned` (a contract delta, below); `anomaly.ts:149-150` keys on `blockedReason`; the SPA shows a
  **poison badge on the Blocked lane** (otherwise poison is invisible — `web/src/types.ts:15` already
  lacks `DEAD_LETTER`).

### Fold 2 — `CANCELLED` → hard delete

Why: a terminal state read only by runs, sprints and incidents (`runs.ts:149,180,282,351`,
`sprints.ts:171`, `incident.ts:148-151`).

- **New tool `delete_task`** (conductor has none; `delete_project` / `deleteProjectRecursive`,
  store `:1393-1445`, is the pattern). Input `{projectId, taskId, version}`; **master** tier; `STALE`
  on version mismatch (`tasks.ts:393` pattern); `CONFLICT_LOCKED` on another identity's live lease
  (`:406`). One transaction: recurse `parentTaskId` children and `runOf` runs → strip the id from every
  dependent's `blockedBy` and blocker's `blocks` → poison-aware auto-unblock of dependents → if it had a
  parent, remove it from the parent's `blockedBy` and auto-unblock → if `runOf`, recompute the parent's
  `racing` (last run gone → READY, `racing:false`, as `cancel_runs` does) → delete events, context
  items, task-scope memory, comments, follow-ups, attachments (+ blob GC), idempotency keys → append a
  board-level `task.deleted{id,title,status}` event, an audit row and a change-log row. `T-n` is never
  reused. A repeat call → `NOT_FOUND`.
- `pick_run` / `cancel_runs` hard-delete the losing runs instead of marking them `CANCELLED`
  (`runs.ts:149,180`); the `run.discarded` event moves to the **parent's** events; `:282/351` and
  `Runs.tsx:20/154/230` become a plain `listRuns`. Tool names and inputs stay — a named semantic
  deviation.
- `list_sprints` "open" → `status !== 'DONE'` (`sprints.ts:171`); incident correlation → `!== 'DONE'`
  (`incident.ts:148-151`); autoclose (store `:1062-1077`) **deletes** the incident task when
  `isUntouched` (`incident.ts:156-164`, BACKLOG|READY and nothing written) and otherwise annotates it;
  a delivery row may then carry a dangling `taskId`, which the oncall screen tolerates.
- Default columns (`src/tools/boards.ts:26`) drop Cancelled.
- Enumeration sites to change: **36 non-test files** — 15 `src`, 13 `web/src` (incl.
  `useTaskDetail.ts:18-27` hard-coded fallback, `types.ts:135,141`, `ticketSearch.ts:26-27` aliases),
  8 `plugin/` (`worker-assigned.sh:7,89`, `master.md:52,77`, `worker.md:33-35`, `runs.md:32`,
  `SKILL.md:295-304,746,806,829`, `tools.md:41-43,83`). The plugin files are **conductor's**, out of
  this repo; they are listed so the plugin adapter ticket (open question 3) has its grep.

Decisions (each reversible; the one-line reason follows the arrow):
- **Relicensing is explicit, not inferred.** Conductor is proprietary (`LICENSE`, `package.json:90`
  `UNLICENSED`). Everything copied into this repo — the trimmed SPA, REST shapes, ported domain rules —
  is **relicensed Apache-2.0 by the owner**; the hosted-only modules (billing, WorkOS, admin, plugin
  maker, metering) stay proprietary → that is the open-core boundary, and it needs the owner's name on
  it, not open question 2's default.
- **`delete_task` is master-tier, which narrows who can abandon a ticket.** Conductor's
  `move_task → CANCELLED` was writer-tier (any member). Default: master-only, because a hard delete is
  irreversible and `delete_project` is the precedent → overrule to writer-tier (own tickets only) if
  agents must be able to abandon their own work without a master.
- **Database: SQLite by default, Postgres when configured** (owner ruling). One setting, `database.url`
  (env `BATONDECK_DATABASE_URL`): unset or a file path → SQLite (`modernc.org/sqlite`, WAL,
  `_txlock=immediate`, hdtp-gateway's DSN); `postgres://…` → pgx pool with goose's session lock. Both
  engines ship in every release and the conformance suite runs on both in the gate → the engine pair is
  a copy from hdtp-gateway; the cost is the doubled `queries/{sqlite,postgres}` files per Store area.
- **Migrations are sequential `000N_*.sql` and the schema lands up front**: P1 writes `0001_base.sql`
  for every in-scope area (the schema is derivable from `store.ts` now), so P5–P9 seldom need one;
  when they do, the lane renumbers at merge and goose's default refusal of out-of-order versions is the
  guard → hdtp-gateway has no `allow-missing`, and reserved ranges would need it.
- **The core calls services directly, not MCP-over-HTTP** → the gateway↔core split existed only to put
  separate Cloud Run services behind IAM.
- **Stateful Streamable HTTP sessions**, so `resources/subscribe` pushes → go-sdk v1.8.0 has
  `ServerOptions.SubscribeHandler` + `UnsubscribeHandler` (both required or it panics,
  `mcp/server.go:109,226-230`) and `Server.ResourceUpdated` (`:1183`). hdtp-gateway runs
  `Stateless=true`; this plan deliberately does not.
- **The board feed is a service, not only a resource** → the BFF's `/feed` route reads it, as
  ui-backend does via `pool.readResource` (`app.ts:3267`).
- **Agent wake** = three paths off one bus (section *Notifications* above): Claude Code **channel**
  (`notifications/claude/channel` from the binary's own `channel` subcommand), standard MCP
  `resources/updated` push, and the `/wake` SSE doorbell with cursor catch-up → replaces GCP Pub/Sub,
  the Stop hook and the background wait with documented protocol surfaces.
- **SQL task counter per project** (`project_counters`, conductor store `:967`), so ids keep the `T-n`
  form, are never reused, and every lookup is keyed by `(project_id, task_id)` → conductor rule 6 / T-111.
- **The transaction is the version bump + event append + audit row + change-log row**, with
  `BEGIN IMMEDIATE` on SQLite and a row lock on Postgres → the same invariant as `runTaskTxnIdem`
  (`store.ts:1186`). Event `type` vocabulary is pinned in one Go file (the `task.poisoned` rename is
  the only departure). Task-list cursors stay base64url `{order,id}` (`store-helpers.ts:31`).
- **Search:** SQLite FTS5 and Postgres `tsvector`; semantic search off → no embedding dependency.
- **Blobs:** local disk behind HMAC-signed upload/download URLs served by the binary itself; S3 later
  → keeps the `attach_file` "uploadUrl" contract.
- **Analytics:** an MCP middleware writes one `tool_calls` row per call with conductor's fields
  (`tool, identity, agent, outcome, code, latencyMs, projectId` — `common.ts:655-695`); `opsQuery`
  becomes SQL over it with `days ≤ 90`, a retention row, and the membership check → replaces BigQuery.
- **OAuth AS:** port `as.ts`'s endpoints with **one stated departure — opaque DB tokens instead of
  RS256 JWTs**, so `jwks_uri` is omitted from the metadata (clients never verify our tokens; `/mcp`
  does). `/authorize` uses the local session login plus a consent page (CSRF on the POST) instead of
  WorkOS. Hardening carried from the review: exact `redirect_uri` match against the DCR record,
  `/register` rate limit + GC of unused registrations, refresh-token rotation with reuse → revoke the
  family, RFC 8707 `resource` binding, and `/mcp` advertising RFC 9728 protected-resource metadata via
  `WWW-Authenticate`.
- **Oncall ingest is in-binary** (`POST /hooks/{integrationId}`), mounted **outside** the session/CSRF
  middleware with `CapBody`, a per-integration rate limit, HMAC dual-accept during rotation
  (`hmac.ts:3-9`), secrets sealed with a keyring KEK (`secret-envelope.ts:31-58`), and delivery/raw-body
  retention (`ingest.ts:86-104`). Incident routing rings the doorbell (`ingest.ts:427`), so P7 depends
  on P3. **The tradeoff:** conductor isolated ingest because a datastore role on a process parsing
  attacker-controlled JSON meant cross-tenant read. Single-workspace removes the cross-tenant blast
  radius, but the parser now shares a process with full DB access. Overrule this if you want a separate
  `batondeck-kanban ingest` process that has a token and no DB access.
- **Contract fidelity** is a comparator, not a vibe. `contract/canonical.go` reduces both sides to
  `{name, properties{typeSet, enum, items, properties, additionalProperties}, required (sorted)}` for
  input **and output** schemas, mapping Zod `anyOf:[T,null]` and Go `type:["null",T]` to one typeSet and
  stripping `$schema, description, default, min/max, pattern, format, propertyNames, propertyOrder`.
  Go-side rules: **optional = value field + `omitzero`** (conductor has 442 `.optional()`),
  **nullable = pointer** (151 `.nullable()`); enums are not inferred, so `Status`, `Priority`,
  `MemoryScope` go through `ForOptions.TypeSchemas`; `customFields` is a `TypeSchemas` override
  (`additionalProperties: anyOf[string≤500, number, boolean]`); nested `additionalProperties:false` is
  emitted by Go structs and matches mcp.json's 458 nested cases; Zod `.refine` (10) become handler
  checks. The test asserts `canonical(conductor) ⊖ deltas.json == canonical(go)` exactly, so every
  ruling above is an explicit, reviewable line in `deltas.json` — e.g.
  `removedEnumValues: ["/tools/move_task/input/properties/status/enum/CANCELLED", …]`, no tolerance
  rule. Note `removedTools` carries **~37 entries** (every out-of-scope public tool), not only the
  three dropped ones; the list is the scope, read it as such. The error codes/shape must equal `src/errors/index.ts`. Conductor's plugin can then **call
  tools** against both; it does **not** get wake for free (it waits on Pub/Sub, `2c58de3e`,
  `5e2baafa`) and cannot know `delete_task`.

## Notifications: MCP + sockets (owner ask 2026-10-22)

The owner's ask: notify locally running Claude Code sessions through what the current MCP protocol and
Claude Code support — channels and sockets — instead of conductor's Pub/Sub listener + Stop hook +
background `wake-wait.mjs` (`plugin/hooks/stop-gate.sh`, `skill/wake-listener/listener.mjs`).

**Wire facts, read from the official Discord channel plugin on this machine**
(`~/.claude/plugins/marketplaces/claude-plugins-official/external_plugins/discord/server.ts`):
- A channel is an ordinary **stdio** MCP server (`StdioServerTransport`, `server.ts:723`) that declares
  `capabilities.experimental["claude/channel"] = {}` (`:443-452`).
- It pushes `notifications/claude/channel` with `params: { content: string, meta: Record<string,string> }`
  (`:875-885`); the session sees it as a `<channel source="…" …meta…>` message (its `instructions`
  block, `:456`).
- It is loaded with `claude --channels plugin:<name>@<marketplace>` (README `:67`); its config lives in
  `~/.claude/channels/<name>/`.
- Optional permission relay: declare `"claude/channel/permission"` and handle
  `notifications/claude/channel/permission_request {request_id, tool_name, description, input_preview}`
  (`:470-500`) — **we do not declare it**: the plugin's own comment says only a server that
  authenticates the replier may, and a task board is not a chat.
- Anything a third party can type (task titles, notes) goes in `meta`, never in `content` — the same
  rule the Discord plugin applies to attachment names (`:871`), because `content` is what the model
  reads as the message.

Content policy carried from conductor's doorbell: the payload is **zero-authority** — it names a task
and a kind; the agent still calls `claim_next` / `get_task_context` and the server still enforces every
check. A woken agent on `broadcast` probes the open frontier as well as its inbox (CLAUDE.md note on
`WakeKind`).

**Confirmed against Claude Code 2.1.308 (local `claude --version`) and its docs** (channels-reference,
channels, mcp, cross-session-messaging, hooks pages; checked 2026-10-22):
- Channels need **v2.1.80+**, a claude.ai or Console API key (**not** Bedrock/Vertex/Foundry), and are
  **stdio only** — Claude Code spawns the process, so the channel cannot be an external daemon; it is
  the `channel` subcommand of our binary, spawned per session.
- Delivery is **queued in order and batched into the next turn when Claude is busy; when idle, it
  starts a new turn.** No acknowledgement. That is what makes the Stop hook unnecessary.
- `meta` keys must match `[A-Za-z0-9_]+`; a hyphenated key is **dropped silently** → we use
  `task_id`, `board_id`, `project_id`, `kind`, `cursor`.
- Loading: `claude --channels plugin:<name>@<marketplace>` registers **only allowlisted plugins**; an
  unlisted server loads with `claude --dangerously-load-development-channels server:<name>` from a
  `.mcp.json` entry. **Both are ignored under `-p` and the SDK**, so an unattended worker cannot receive
  a channel → it gets path A2 or C below.
- Org controls `channelsEnabled` / `allowedChannelPlugins` can block a channel; a blocked channel
  drops events **with no error** → the `channel` subcommand logs every push to stderr and the UI shows
  the session's last-delivered cursor, so silence is visible.
- The v2 MCP runtime negotiates protocol **2026-07-28**, which go-sdk v1.8.0 also offers as its latest
  (`mcp/shared.go:50-62`, with 2025-11-25 / 2025-06-18 / 2025-03-26 behind it). The guide reports that
  a channel server negotiating 2026-07-28 **is not registered** on the v2 runtime and names
  `MCP_PROTOCOL_NEGOTIATION=legacy` as the workaround — **P11's first task proves registration** against
  2.1.308 and, if it fails, pins the server's accepted version to 2025-11-25 rather than asking users
  to set an env var. A mutation-proven check, not a guess.
- Whether Claude Code subscribes to MCP resources (`notifications/resources/updated`) is
  **UNCONFIRMED** in the docs → path B is designed for other MCP clients; Claude Code sessions use A
  (interactive) or A2/C (headless). The docs name a `ws` transport "for servers that push events
  unprompted" — noted, not adopted.

**Sockets — two documented ones, both used:**
- **The orchestrator's Unix domain socket** alongside TCP (`listen: ["tcp://:8080",
  "unix:///run/batondeck/batondeck.sock"]`, hdtp `internal/core/adminsock.go` pattern): the same HTTP
  mux (MCP, REST, `/wake`) over both. Socket auth = file mode `0600` plus the peer-credential check
  (`SO_PEERCRED` / `LOCAL_PEERCRED`); the bearer token is still required for **board identity**, the
  socket only removes network exposure. `curl --unix-socket` works for ops. Claude Code has no
  documented Unix-socket MCP transport, so the `channel` subcommand is the bridge.
- **Path A2 — Claude Code's per-session inbox socket** (documented in cross-session-messaging,
  **v2.1.224+**): every session binds a Unix socket exposed as `CLAUDE_CODE_MESSAGING_SOCKET` with
  `CLAUDE_CODE_MESSAGING_TOKEN` (the auth line is optional on macOS/Linux); a message is read between
  tool calls during a turn or **starts a new turn when idle**, governed by `crossSessionInbound`
  (`accept|hold|refuse`). This is the door for sessions that cannot run a channel (`-p`, SDK,
  Bedrock/Vertex): a SessionStart hook posts the socket path + token to the **local** orchestrator over
  its own Unix socket (`POST /internal/wake-session`, never over TCP), and the orchestrator writes the
  doorbell straight to the session's inbox. **The payload format after the auth line is UNCONFIRMED**
  → P11 reads it from Claude Code's own `SendMessage` traffic before building, and if it is not stable,
  A2 is replaced by an `asyncRewake: true` command hook (exit 2 wakes Claude; stderr shown as a system
  reminder) — also documented, idle-only semantics UNCONFIRMED.
- `claude -p --resume <id>` / `--continue` open a **new** process; they do not inject into a running
  session, so they are not a wake path.

**Coalescing and cost:** one doorbell per `(token, kind)` per 250 ms window; `/wake` and channel
subscribers are in-memory maps keyed by token, fed by the bus, so an idle watcher costs **0 queries**;
the SQLite bus poll runs only while a subscriber exists (Postgres uses `LISTEN/NOTIFY`).
